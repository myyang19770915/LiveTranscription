## 目標：閉環

```
會前帶出未完成事項 → 會中轉錄（時間、說話者、偵測進度）→ 會後校對逐字稿
→ AI 抽決議／待辦（附證據句）→ 人工確認 → 發佈 → 追蹤 → 下次會前
```

## P1 設計

### 1. 轉錄、轉譯、錄音三者對應

- **錄音改由伺服器端存**：gateway 本來就收到送往 ASR 的每一個 PCM16 位元組，直接寫成 `output/<meeting>.wav`（或轉 FLAC／Opus）。錄音和 ASR 用的是**同一份音訊**，時間軸天生對齊；瀏覽器 MediaRecorder 保留作為備援。
- **時間戳**：gateway 計算已收到的音訊位置（位元組數 ÷ 32 = 毫秒），每個送回瀏覽器的辨識事件都附上 `audioMs`。
- **段落時間**：前端記錄每段文字第一次出現時的 `audioMs`（起點）與定稿時的 `audioMs`（終點）。ASR 有延遲，播放時前後各多放約 0.5–1 秒；之後可再用強制對齊（forced alignment）把邊界修得更準。
- **對應關係**：一個段落 = 一段音訊區間 + 轉錄原文 + 譯文，用同一個段落 id 串起來；會議結束時存成結構化資料，不再只有純文字。

### 2. 會後校對與修改紀錄

- **校對頁**：列出每個段落（時間、原文、譯文）；點段落就播放該段錄音，可調整前後播放範圍。
- **修改轉錄**：改完按確認，**自動重譯該段**，策略與現行精修相同：前兩段原文與譯文作上下文、附後文、會議詞彙、自動學習詞彙、可選雲端精修、防重複檢查。修改後下一段的「前文」也變了，可選擇一併重譯下一段。
- **修改紀錄**（每次修改一筆，不覆蓋）：段落 id、音訊區間、ASR 原始文字、修改後文字、修改前後譯文、語言、辨識引擎、修改時間。另記一筆狀態：已確認／未確認。
- **匯出微調資料**：`段落音訊.wav + 修正後文字` 輸出成 JSONL，可直接用於 ASR 微調；修改前後的差異也能拿來統計常見錯誤，並回饋進會議詞彙。

### 3. 資料表（Postgres；另需 `users`、`teams`、`team_members`，每筆會議帶 `team_id`）

| 表 | 主要欄位 |
|---|---|
| `meetings` | 標題、系列、時間、與會者、語言、引擎、錄音路徑 |
| `segments` | 會議、序號、開始／結束 ms、說話者、原文、譯文、是否已確認 |
| `segment_edits` | 段落、修改前後原文、修改前後譯文、修改時間、修改者 |
| `items`（P2） | 類型（決議／待辦／問題／風險）、內容、負責人、到期日、狀態、證據段落、來源會議、確認者 |
| `item_updates`（P3） | 事項、會議、狀態變化、證據段落 |
| `people`（P2） | 名字、別名 |

## 原則

- 每條決議／待辦都要附證據句，能點回原文與錄音。
- AI 只能提出，人確認後才是正式紀錄；負責人對不到就標「未指派」，不要讓 AI 猜。
- 到期日以會議日期換算實際日期，並保留原話。
- 會議內容優先用本機模型處理；會後翻譯模型閒置，可直接拿來做抽取。GPU 已用約 30/32 GB，不再加新模型。
- 先在系統內追蹤，流程穩定後再串外部工具。
