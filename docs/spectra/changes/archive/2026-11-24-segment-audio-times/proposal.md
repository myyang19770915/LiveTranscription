## Problem

在逐字稿校對頁播放錄音時，聲音和段落對不上（使用者 2026-11-24 回報，會議 `6ec5d47e-995a-493f-90a1-bab117838304`）：
- 點某一段播放，聽到的是前一句的尾巴或一段空白，要等幾秒才是那一段。
- 在發言時間軸點某次發言播放，下方被標示的段落不是正在講的那一段。

## Root Cause

精準模式的段落時間是估的，不是量的。`quality_pass.allocate()` 把一個音訊區塊的時間，依字數比例分給區塊裡的句子，前一個區塊留下來還沒成句的文字也算在內。句子之間的停頓、語速變化都不會反映在時間上。

用這場會議的錄音量測（從音量找出停頓後開口的時間點，量測值）：

| 段落 | 目前存的開始時間 | 實際開口 | 差距 |
| --- | --- | --- | --- |
| API 提供一百萬 token… | 5,448 ms | 約 7,460 ms | 早 2.0 秒 |
| 思考強度分為 low… | 17,578 ms | 約 21,380 ms | 早 3.8 秒 |
| API 的標準價格… | 44,040 ms | 約 45,800 ms | 早 1.8 秒 |
| 我這次是在 Anti Gravity… | 58,237 ms | 約 59,540 ms | 早 1.3 秒 |

一般模式（即時辨識引擎）的段落時間則是文字出現的時間，比說話晚約 1 秒，播放時靠固定往前 3 秒來補。

會後自動執行的說話者辨識（MOSS-Transcribe-Diarize）已經存下每次發言的起訖時間和文字。同一場會議中，它的發言開始時間和錄音量到的開口時間差 0.1～0.5 秒（量測值：830／800、7,380／7,460、21,330／21,380、35,370／35,440、45,750／45,800、59,660／59,540 ms）。這份時間目前只用來畫時間軸和標說話者，沒有用來校正段落時間。

## Proposed Solution

說話者辨識完成時，用它的發言時間校正每個段落的起訖時間：

- 把段落文字和附近的發言文字逐字比對（沿用標說話者時的比對方式）。比對到的第一個字和最後一個字，各自落在某次發言的某個位置，依該次發言的時間按比例換算成段落的開始與結束時間。
- 比對到的字數不到段落的一半時，這個段落不校正，維持原本的時間。
- 校正過的段落標記為「時間來自錄音」（`segments.timed`）。這種段落播放時只往前多放 0.3 秒、往後多放 0.3 秒；沒校正過的段落維持往前 3 秒、往後 0.5 秒。時間軸播放時標示目前段落的判斷也一樣分兩種。
- 按「重新辨識」會再校正一次。
- 提供一個指令，替已經有說話者辨識結果的舊會議補做校正。

## Non-Goals (optional)

- 不引入對齊模型（例如 Qwen/Qwen3-ForcedAligner-0.6B）。理由：現有的發言時間已經在 0.1～0.5 秒內；顯示卡 32 GB 已用 30 GB（量測值），要另外架一個服務；該模型單次處理長度有限，還要自己切段。校正後若仍不夠準，再另開變更評估。
- 不改會議進行中的時間估算（`allocate()`）。會議中沒有發言時間可用；校正在會後進行。
- 不做逐字的時間（字級高亮）。
- 沒有錄音、或說話者辨識沒完成的會議，維持現狀。

## Success Criteria

- 會議 `6ec5d47e…` 補做校正後，上表四個段落的開始時間與實際開口時間的差距都在 0.6 秒以內。
- 校對頁點一個校正過的段落，播放從該段開始時間前 0.3 秒開始。
- 時間軸播放到某次發言時，下方標示的是文字相符的那個段落。
- 文字比對不到的段落，時間與播放範圍和現在完全一樣。
