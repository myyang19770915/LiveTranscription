## Context

搜尋頁（webapp/static/search.js）每次 `run()` 遞增 `latest`，回應回來時比對票號，較舊的回應直接丟掉；但送出到回應之間畫面完全不變。後端 `terms_of` 用 `q.split()[:MAX_TERMS]` 靜默截斷。

## Goals / Non-Goals

**Goals:**

- 送出後立刻讓輔助技術知道「正在忙」，慢的查詢有看得到也聽得到的提示，舊結果不會被當成新結果。
- 5 個詞上限前後端同一規則、同一句訊息。

**Non-Goals:**

- 不改搜尋演算法、排序、300 筆上限與篩選語意。
- 不做邊打字邊搜尋（仍是送出或切換篩選才查）。
- 不用 AbortController 取消舊請求：票號已能保證結果正確，取消只省流量，留待需要時再做。

## Decisions

### 載入狀態：立即標記、延遲宣告

送出時立刻在結果區設 `aria-busy="true"` 與 `is-loading` class（舊結果 `pointer-events: none`，透明度經 150 ms 延遲轉場才變淡），摘要文字則在 200 ms 後才改成「正在搜尋「…」…」。快的查詢（多數 < 200 ms）因此不會閃爍，也不會讓 `aria-live` 摘要連續播報兩次；慢的查詢一定有提示。只有最新票號能解除載入狀態，較舊回應抵達時什麼都不做。

### 超過上限：前端擋下、後端 422

前端以 `/\s+/` 切詞（含全形空白，與 Python `str.split()` 對 CJK 文件一致）；超過 5 詞或去空白後超過 100 字就不送出，清除舊結果與摘要，以 `role="alert"` 的提示顯示與後端相同的訊息，搜尋框設 `aria-invalid="true"` 並以 `aria-describedby` 指向提示。網址照常更新，分享出去的網址打開也會看到同樣提示。後端改為 `len(terms) > MAX_TERMS` 回 422，避免直接呼叫 API 時靜默截斷。

**替代方案**：輸入時即時提示詞數。捨棄原因：中文使用者常整句貼上再刪減，打字中途跳警示干擾較大；送出時提示已足夠清楚，初始說明也寫明上限。

## Risks / Trade-offs

- [舊結果在 200 ms 內仍可見] → 已設 `aria-busy` 與不可點，視覺上 150 ms 後變淡。
- [前後端切詞規則若有差異] → 兩邊的訊息相同，且 e2e 驗證前端不送出、單元測試驗證後端 422，全形空白兩邊都算分隔。
